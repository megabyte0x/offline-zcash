# Offline Meshes Carry Zcash Claims, Not Coins

The system can be built on today's Zcash testnet, but what crosses the mesh without internet is not settled ZEC. It is a fully signed and proven Ironwood transaction that the recipient can verify but the sender can still revoke. Value moves only when a gateway pushes that transaction to the public testnet and a block includes it. The recommended architecture has four layers. The first is an authenticated IP radio backbone between the physical basecamps (5 GHz point-to-point links, Wi-Fi HaLow, 802.11s with batman-adv). On top of it runs a private, internet-free Logos Delivery v0.39.x network: no preset, a private cluster ID, static peers, RLN and Mix turned off, two-week Store retention, and application-level sign-then-encrypt envelopes padded to one fixed size on a single shared topic. Payments are v6 Ironwood-only transactions built through PCZT v2, proved locally, and signed on a hardware or FROST signer. Finally, two or more gateways broadcast over Tor and return signed inclusion proofs. Ironwood suits delayed settlement better than most people assume. Consensus sets **no maximum anchor age**, so a basecamp that has been out of sync for days still builds valid spends. The Halo 2 prover needs no downloaded parameters. And a typical 2-action payment is **9,166 bytes**, about 6% of Logos's default 150 KiB message limit. The hard limit is double-spending. No offline recipient can prove a note is unspent, so the design uses tiered acceptance. A payment is "pending" when it arrives, "locally final" only after a FROST co-signer holding half the spend authority attests to it, and "final" after on-chain confirmations. The expiry now recommended on NU7 testnet (120 blocks: about 50 minutes at the target block rate, about 2 hours at the observed rate) is far too short for store-and-forward, so the whole fleet has to set one expiry derived from how often a gateway gets an uplink. Amounts and recipients stay cryptographically hidden. Metadata is the weak point: the gateway is the first visible broadcaster, stale anchors leave fingerprints, neighbours can time messages on a small mesh, and radios can be located by direction finding. The design reduces these leaks but cannot remove them. One naming note: "basecamp" in this report means a physical site. **Logos Basecamp** is an unrelated Logos desktop launcher app, and this design deliberately does not use it.

## Four layers turn radio links into a payment path

The architecture keeps three jobs apart. Moving IP packets between camps is the physical layer's job. Moving opaque, encrypted payment envelopes reliably and in store-and-forward fashion is Logos Delivery's job. Creating, verifying and settling value is the job of Zcash and the gateways. Each layer can then be swapped or hardened without touching the others, and no relay or radio ever holds a key that can spend or view funds.

| Layer | Recommended choice | Role | Key numbers |
|---|---|---|---|
| Physical backbone | 5 GHz PtP where there is line of sight; Wi-Fi HaLow (US) where there is not; 802.11s + batman-adv or Babel for path redundancy; authenticated link layer | Carries IP between basecamps and gateways | 450+ Mbps PHY at 7 W (LiteBeam class); HaLow 1.3–2 Mbps at 15.9 km |
| Fallback transport | Reticulum/LXMF over RNode LoRa; QR codes or USB courier | Carries only the Zcash payload bytes, through an application bridge | 9,166 B ≈ 46 LoRa frames ≈ 99 s of airtime at LongFast |
| Messaging | `logosdeliverynode` v0.39.2, Core mode, private cluster | Store-and-forward pub/sub among basecamps and gateways | 150 KiB maximum message; Store retention raised to 14 days |
| Payment envelope | Sign-then-encrypt with in-person-provisioned keys; fixed padding; one shared topic; trial decryption | Hides who pays whom from relays and Store nodes | One fixed 16 KiB envelope size for all payment traffic |
| Zcash | v6 Ironwood-only transactions via PCZT v2; local Halo 2 proving; Keystone or FROST signing | Creates the claim and lets the recipient verify it | 2 actions; branch ID `0x77190AD9` |
| Settlement | Two or more gateways: zebrad 7.x + Zaino or Zebra's built-in gRPC server; submission over Tor | Broadcasts, returns proofs, redistributes chain state | 1,487 B per header; inclusion proof about 1.7 KB |

### An IP backbone, not LoRa, has to carry Logos

Logos Delivery is IP-only. It runs over TCP, QUIC (on by default since v0.39.0) and WebSocket. No source shows a BLE, LoRa or other non-IP transport, implemented or planned ([v0.39.0 release](https://github.com/logos-messaging/logos-delivery/releases/tag/v0.39.0); [Logos transports](https://docs.logos.co/messaging/concepts/transports)). Tunnelling libp2p over LoRa fails on arithmetic alone. Connection setup costs about 3 KB: TCP, multistream-select, the Noise XX handshake, muxer negotiation, and an identify exchange of "a couple of kilobytes" ([funkpost analysis](https://github.com/NiKrause/funkpost/issues/1)). At Meshtastic LongFast that is about **32 seconds of airtime and about 54 minutes of wall-clock time** under the EU 1% duty cycle. GossipSub then sends a heartbeat every second to a fan-out of D=6 peers, indefinitely ([gossipsub v1.0 spec](https://github.com/libp2p/specs/blob/master/pubsub/gossipsub/gossipsub-v1.0.md)). The only libp2p-over-LoRa transport found states that it has "absolutely no security" ([libp2p-lora-transport](https://github.com/RTradeLtd/libp2p-lora-transport)).

So the backbone has to be IP radio. Where line of sight exists, LiteBeam-class 5 GHz bridges deliver **450+ Mbps at 7 W** for €55–75 per end ([NetXL](https://www.netxl.com/point-to-point-wireless/ubiquiti-lbe-5ac-gem2-litebeam-ac-gen-2-5ghz-23dbi-radio.md)). Where foliage or terrain blocks 5 GHz in the US, Wi-Fi HaLow has reached 15.9 km line of sight at an average of 1.31 Mbps ([Rethink Research](https://rethinkresearch.biz/articles/morse-micro-nets-wifi-halow-range-record/)). The EU is different. HaLow there is capped at 25 mW ERP, 1 MHz channels and a **2.8% hourly duty cycle for stations**, about 100 seconds of transmit time per hour ([Igor'sLAB](https://www.igorslab.de/en/wi-fi-halow-with-kilometer-range-why-the-new-gl-inet-halowlink-2-is-reaching-its-limits-in-europe/)). European deployments should therefore rely on 5 GHz. HaLow's own relay function stops at two hops ([IEEE 802.11ah](https://en.wikipedia.org/wiki/IEEE_802.11ah)), so multi-camp paths need 802.11s/batman-adv or Babel on top. Single-radio meshes lose about half their throughput at the first hop and more after that ([batman-adv list](https://lists.open-mesh.org/mailman3/hyperkitty/list/b.a.t.m.a.n@lists.open-mesh.org/thread/HRSUFGGQ36RAYYJZAHASQILFRF3WYYWX)). Each backbone link should therefore use a dedicated radio pair. Admission control belongs at this layer. An encrypted, authenticated link layer (WPA3 is available on HaLow units such as the GL.iNet HaLowLink 2) means only provisioned radios can join the IP mesh. That matters because Logos Delivery itself has no peer allowlist in the sources reviewed.

LoRa is the fallback for when the backbone fails. It should carry transactions and short notices, never Logos itself. Reticulum is the better stack for this. It needs only a 500-byte MTU, sets up an encrypted link in 297 bytes, keeps working down to 5 bit/s, and its Resources layer handles segmentation and retransmission. LXMF Propagation Nodes add store-and-forward with 111 bytes of overhead per message ([Reticulum manual](https://reticulum.network/manual/understanding.html); [LXMF](https://github.com/markqvist/LXMF)). A gateway service on each basecamp re-encodes only the 9,166-byte transaction into LXMF. That is about **99 seconds of airtime at LongFast: 16.5 minutes of wall-clock time in the EU's 869.4–869.65 MHz 10% sub-band, or 2.8 hours in a 1% band** ([Meshtastic presets](https://meshtastic.org/docs/overview/radio-settings/); [TTN duty cycles](https://www.thethingsnetwork.org/docs/lorawan/regional-limitations-of-rf-use/)). Meshtastic is a poor substitute. A DEF CON 34 talk showed that it ships a default shared key, sends cleartext headers, and allows forgery ([DEF CON 34 HRV](https://cfp.hamvillage.org/dc34/talk/CTMAYM/)), and CVE-2025-52464 cloned key pairs across vendor-flashed devices ([NVD](https://nvd.nist.gov/vuln/detail/CVE-2025-52464)). With no radio at all, the same payload fits in four maximum-size static QR codes (2,953 bytes each) or a short animated fountain-coded UR loop ([Blockchain Commons](https://developer.blockchaincommons.com/animated-qrs/)). Amateur radio is off the table: 47 CFR 97.113(a)(4) bans "messages encoded for the purpose of obscuring their meaning", and a shielded transaction is mostly ciphertext ([47 CFR 97.113](https://www.law.cornell.edu/cfr/text/47/97.113)).

Power budgets are modest. A Raspberry Pi 5 basecamp core idles at about 3 W and draws about 8.8 W under full CPU load ([raspberry.tips](https://raspberry.tips/en/faq/raspberry-pi-power-consumption-update-2026-all-models-compared)). Adding a 5 GHz radio, a router and an RNode gives about 13 W, or roughly 312 Wh per day. A 150–200 W panel and a 100 Ah LiFePO4 pack cover that with about three days of autonomy. A gateway with a Starlink Mini adds 20–40 W during each uplink window ([Outcamp](https://outcamp.com.au/blogs/starlink-education-guide/starlink-mini-power-consumption-12v-batteries-runtime)).

### An internet-free Logos network starts from no preset and static peers

Every built-in Logos Delivery preset (`twn`, `logos.dev`, `logos.test`, `status.prod`, `status.staging`) hard-codes entry and mix nodes as `dns4` hostnames on Status-operated internet fleets. TWN also needs a Linea Sepolia RPC endpoint to validate RLN ([networks_config.nim](https://github.com/logos-messaging/logos-delivery/blob/master/logos_delivery/waku/factory/networks_config.nim)). An internet-free network therefore starts from no preset at all. With no preset, the node defaults to one auto-shard, a 150 KiB maximum message size and no RLN validation ([MESSAGING-API](https://lip.logos.co/messaging/application/raw/messaging-api.html)). The operator guide confirms that a network is defined either by a preset or by `--cluster-id` plus `--num-shards-in-network` ([run-messaging.md](https://github.com/logos-messaging/logos-delivery/blob/master/docs/operators/how-to/run-messaging.md)).

| Setting | Value | Reason |
|---|---|---|
| Software | `logosdeliverynode` v0.39.2 (pinned), Core mode, `--entry-layer=channels` | Gives reliable channels (SDS, segmentation, pluggable cipher). v0.39.0 broke the binary name, the env prefix and the C ABI, so pin exact versions. |
| Network identity | No `--preset`; private `--cluster-id` (not 1, 2, 3 or 16); `--num-shards-in-network=1` | Isolates the fleet from public fleets and their `dns4` dependencies |
| Peering | `--nodekey` for a stable peer ID; static `--entry-node=/ip4/<mesh-ip>/tcp/60000/p2p/<id>` lists | A small fixed fleet needs no discovery traffic |
| Discovery | discv5, peer exchange, DNS discovery and Kademlia all off | There is no internet. Peer exchange lets a malicious responder steer peers toward an eclipse. |
| RLN | Off (the default with no preset) | Shipped backends need an Ethereum RPC (`rln_evm`) or a Logos LEZ host (`rln_lez`). Turning it off also removes the stale-root and double-signal leaks. |
| Mix | Anonymity level `None` | Code minimum is 4 mix nodes and the spec recommends 100 or more. The 3,984-byte Mix payload is smaller than a 9,166-byte transaction. |
| Store | `--store=true` on every basecamp core and gateway; SQLite; `--store-message-retention-policy=time:1209600` | Default retention is 2 days. Retention must exceed the longest expected partition. |
| Store Sync | `--store-sync=true`, with `--store-sync-range` raised well above the 3,600 s default | Store Sync is designed for outages of 1 hour or less |
| Reliability | `--reliability` on, with at least two Store nodes reachable | The `sent` event requires a *different* Store node to confirm |
| QUIC | `--quic-support=false` on lossy radio paths | QUIC is on by default since v0.39.0, with a 3-second TCP fallback when UDP fails |
| Messages | Never `ephemeral`; one shared content topic; fixed 16 KiB envelopes | Ephemeral messages are never stored. A shared topic maximises k-anonymity. |

An illustrative launch line is below. Verify it against `--help` for the pinned build, because the CLI changed between v0.38 and v0.39:

```bash
logosdeliverynode --entry-layer=channels \
  --cluster-id=4242 --num-shards-in-network=1 \
  --nodekey=<per-node-hex> \
  --entry-node=/ip4/10.10.0.2/tcp/60000/p2p/<peerId-camp-B> \
  --entry-node=/ip4/10.10.0.9/tcp/60000/p2p/<peerId-gateway-1> \
  --discv5-discovery=false \
  --store=true --store-message-db-url=sqlite:///var/lib/logos/store.db \
  --store-message-retention-policy=time:1209600 \
  --store-sync=true --store-sync-range=86400 \
  --reliability=true --quic-support=false
```

Store and channel settings need care, because Logos Delivery is a real-time pub/sub system with bounded catch-up, not a delay-tolerant network. By its own spec, Store Sync is "designed for short-term offline periods (no more than 1 hour)", and Store Resume recommends at most 6 hours ([WAKU-STORE-SYNC](https://lip.logos.co/messaging/core/raw/store-sync.html)). Reliable channels default to a 5-second acknowledgement timeout and 5 retransmissions ([delivery module docs](https://docs.logos.co/messaging/delivery/use-logos-delivery-module-api-from-app)). That is about 25 seconds of retrying, which is useless across a partition that lasts a day. Multi-day partitions therefore rest on three things: long Store retention, Store backfill when a node reconnects (`backfill-request-timeout-seconds` can go up to 300), and an application-level resend loop keyed by txid. Resending is free because a signed transaction is idempotent ([configure-store.md](https://github.com/logos-messaging/logos-delivery/blob/master/docs/operators/how-to/configure-store.md); [messaging_conf.nim](https://github.com/logos-messaging/logos-delivery/blob/master/logos_delivery/api/conf/messaging_conf.nim)). Reliable channels are labelled "Developer Preview, not feature-complete", so treat them as an optimisation and not as the guarantee.

Payload confidentiality has to come from the application. "The network applies no default encryption to message payloads", and only node-to-node links use libp2p Noise ([Logos FAQ](https://docs.logos.co/messaging/get-started/faq)). v0.39 reliable channels accept an app-supplied authenticated cipher that fails closed rather than falling back to plaintext. With no cipher set, though, the channel is plaintext ([channel_encryption.nim](https://github.com/logos-messaging/logos-delivery/blob/master/logos_delivery/channels/encryption/channel_encryption.nim)). Logos Chat is version 0.1.0, explicitly pre-1.0 and unaudited ([logos-chat](https://github.com/logos-messaging/logos-chat)). The envelope should therefore be the application's own. Each basecamp gets a static X25519 key and an Ed25519 signing key, exchanged in person at setup. Every payment message is signed by the sender's basecamp key, then encrypted (for example with a Noise KK-style pattern), padded to 16 KiB, and published on one shared topic such as `/basecamp/1/payments/proto` with no cleartext recipient field. Every camp receives every envelope and trial-decrypts it against the small set of known peers, much as Zcash wallets trial-decrypt notes. Relays and Store nodes then see only that fixed-size messages exist and when they were sent.

Two practical notes on hosts. The Logos Basecamp desktop app needs 4 GB of RAM at minimum (8 GB recommended), and the delivery module it hosts is documented only with the internet-backed `logos.test` and `logos.dev` presets ([Install Basecamp](https://docs.logos.co/basecamp/install-logos-basecamp); [delivery module docs](https://docs.logos.co/messaging/delivery/use-logos-delivery-module-api-from-app)). The headless node is the right tool: a relay-only node needs about 0.5 GB of RAM, with 2 GB recommended ([docs.waku.org](https://github.com/logos-messaging/docs.waku.org/blob/develop/docs/run-node/index.md)). Phones can run Edge mode attached to their own camp's Core node. That reveals the phone's peer ID and topics only to its own operator.

### Ironwood v6 tolerates stale chain state but not stale epochs

Ironwood is the shielded pool introduced by **NU6.3**, not NU7. It activated on **testnet at height 4,134,000** (branch ID `0x37A5165B`) and on mainnet at 3,428,143, around 28 July 2026 ([ZIP 258](https://zips.z.cash/zip-0258)). It is a second value pool of the Orchard protocol. It shares Orchard's Action encoding, Halo 2 proof system, keys and unified addresses. It has its own note commitment tree, nullifier set and value balance, and every output uses the quantum-recoverable `0x03` note plaintext ([ZIP 229](https://zips.z.cash/zip-0229); [ZIP 2005](https://zips.z.cash/zip-2005)). Since NU6.3, no new value may enter the Orchard pool, and wallets "MUST NOT send funds to any external receiver ... in the Orchard pool" ([ZIP 326](https://zips.z.cash/zip-0326)). "Ironwood only" therefore means v6 transactions whose only shielded component is `vActionsIronwood`, sent to ordinary `utest…` unified addresses. The pool is selected by the transaction component, not by the address.

Testnet has also passed **NU7, at height 4,465,026, in early October 2026**. New transactions must carry branch ID **`0x77190AD9`**, v4 transactions are invalid, the target block spacing is 25 seconds, and Zebra 7.0.0-rc.0 drops peers that advertise a protocol version below 170180 ([Zebra releases](https://github.com/ZcashFoundation/zebra/releases); [ZIP 218](https://zips.z.cash/zip-0218); [ZIP 2003](https://zips.z.cash/zip-2003)). The working stack is:

- zebrad 7.0.0-rc.0 or later;
- Zaino 0.10.x (Ironwood support since 0.6.0) or Zebra's experimental built-in lightwalletd gRPC server;
- Zallet 0.1.0-beta.3, which added PCZT JSON-RPC methods ([Zaino releases](https://github.com/zingolabs/zaino/releases); [Zallet releases](https://github.com/zcash/wallet/releases)).

zcashd does not implement NU6.3. Two caveats affect planning. First, Zallet's release notes mention neither testnet nor NU7, so a wallet able to transact on testnet after NU7 is the first thing to verify. Second, the public testnet explorer shows **no Ironwood pool at all**, so pool state has to be read from a local zebrad `getblockchaininfo` ([testnet explorer](https://testnet.zcashexplorer.app/)).

To construct a transaction offline, the sender needs:

- the spend authorizing key;
- the full viewing key;
- the plaintext of each spent note;
- a 32-level Merkle witness to *any* earlier final Ironwood treestate root (the anchor);
- the branch ID;
- an expiry height;
- a fee.

The anchor rule is lenient. ZIP 258 requires only that `anchorIronwood` refer to "some earlier block's final Ironwood-pool treestate", with no age bound, and Zebra accepts any historical root ([ZIP 258](https://zips.z.cash/zip-0258)). A basecamp that last synced a week ago therefore still builds valid spends, as long as the anchor block stays on the best chain. PCZT v2 goes further. In v6 the anchor is authorizing data rather than effecting data. A transaction can be fully signed *before* an anchor is chosen, and re-anchored without changing its txid. It can even be signed while spending a note from a parent transaction that has not yet been mined, with the witness and proof supplied after the parent confirms ([ZIP 374](https://zips.z.cash/zip-0374)). Expiry, values and the branch ID are effecting data, fixed at signing.

The Prover role needs a lot. It requires each spent note's plaintext, the full viewing key and the witness, and ZIP 374 warns that delegating proving "reveals the private data of the notes being spent or created" to the prover ([ZIP 374](https://zips.z.cash/zip-0374)). **Proving must therefore stay on the payer's own builder, never on a gateway or a shared "prover node".** Fortunately it is cheap enough. The Orchard-protocol circuit is Halo 2 at K=11 and needs no downloaded parameters. Two actions prove in 0.3–1.35 seconds on an M4 Max and verify in about 4–12 ms ([dashpay/orchard PR #13](https://github.com/dashpay/orchard/pull/13)). iPhones take more than 3 seconds on today's stack. A vendor claims about 200 ms with the new Zakura stack ([CoinInsider](https://www.coininsider.org/news/zcash-proving-times-reach-around-200ms/)). No Raspberry Pi figure exists, so it has to be benchmarked.

Signing can move to an air-gapped Keystone. Zodl says firmware 3.0.2 or later is required for Ironwood ([Zodl support](https://support.zodl.com/article/49-upgrading-keystone-firmware)). Ledger's PCZT flow keeps the binding signature, and therefore knowledge of all amounts, on the host ([Ledger docs](https://developers.ledger.com/docs/device-interaction/dmk-ts/references/signers/zcash)).

A 1-input/2-output payment pads to 2 actions and serializes to **9,166 bytes**. Of that, 7,264 bytes is proof. Each additional pair of actions adds 6,312 bytes ([ZIP 229](https://zips.z.cash/zip-0229)). Fees under ZIP 317 count logical actions, with a minimum of 2. Zebra 6.4.0 and later admits 1,000 zats per action, and test networks report 1,000 from `getstandardfee`, while ZIP 317's text still lists 5,000 ([Zebra releases](https://github.com/ZcashFoundation/zebra/releases); [ZIP 317](https://zips.z.cash/zip-0317)). A non-standard fee is a fingerprint, so the fleet should use one value. 2,000 zats matches what Zebra reports today, but it should be confirmed against what Zallet actually emits.

Two constraints govern the timing of offline transactions. The first is expiry. ZIP 218 recommends raising the default expiry delta from 40 to 120 blocks at NU7 ([ZIP 218](https://zips.z.cash/zip-0218)). That is 50 minutes at the 25-second target, and about 2.0–2.2 hours at the roughly 61–67-second spacing observed on testnet since NU7. Either way it is far shorter than a multi-hop LoRa path or a once-a-day gateway uplink. The fleet should set one expiry delta from gateway cadence, converted to blocks at the **25-second target**. A slower chain only lengthens the wall-clock window, so the target rate gives the lower bound. Daily uplinks plus a two-day margin come to 3 × 3,456 = **10,368 blocks**: three days at target, about seven days at today's observed rate. `nExpiryHeight = 0` disables expiry, but it lets a withholding gateway release a transaction arbitrarily late, and Zebra's handling of it is unverified.

The second constraint is the branch-ID epoch. Txids and signature hashes commit to the consensus branch ID ([ZIP 229](https://zips.z.cash/zip-0229)). A transaction signed under NU7 becomes permanently invalid if another upgrade activates before it is mined, and re-anchoring cannot rescue it. No post-NU7 testnet upgrade is scheduled. Gateways should still distribute the upgrade schedule, and expiry must never straddle a known activation height.

One wallet-management consequence is easy to miss. Change from an unmined transaction can be *signed* but not *proved* until the parent is mined, because no witness exists yet. A basecamp's offline spending capacity is therefore the set of confirmed notes it held at its last sync. Before deployment, while connected, each basecamp should split its balance into ten or more notes of common denominations. Shielding early and in round amounts also blunts the amount-correlation leak at the transparent-to-Ironwood boundary. Testnet TAZ usually arrives transparent, so the amount it shields is public ([Zodl support](https://support.zodl.com/article/56-what-is-the-ironwood-shielded-pool)).

On the receiving side, a basecamp with only the transaction bytes and its own keys can check a lot offline:

- trial-decrypt its output with its incoming viewing key;
- recompute the note commitment and compare it with `cmx`;
- verify the spend-authorization and binding signatures;
- verify the Halo 2 proof against a locally derived verifying key.

Together, these establish that *if* the anchor is a real Ironwood root, the spent notes existed, the nullifiers are correctly derived, and value balances. The recipient cannot verify three things. The first is that the anchor is real. Without chain data, an attacker can prove against a fabricated tree. The second is that the nullifier is not already on chain. The third is that the sender will not later broadcast a conflicting spend. A camp that keeps PoW-validated chain state closes the first gap and narrows the second to "as of last sync". The third cannot be closed, which is the subject of the next section. ZIP 221 history leaves now commit to `hashLatestIronwoodRoot` ([ZIP 258](https://zips.z.cash/zip-0258)). In principle, an MMR inclusion proof over a relayed header chain could therefore prove an anchor is real at SPV cost, but no tool for this exists yet.

### Gateways settle, prove inclusion, and feed chain state back

A gateway is any basecamp that sometimes has an uplink: a duty-cycled Starlink Mini, a cellular modem, or a courier who carries a USB stick to town. It runs zebrad 7.x plus Zaino or Zebra's built-in `CompactTxStreamer` gRPC server. The prior-art record sets two rules here. The first is that projects tied to one operator's relay died with that operator. goTenna was acquired by defense firm Forterra in 2025 and repositioned for military and emergency users ([Breaking Defense](https://breakingdefense.com/?p=66822)), and Samourai's pushTx relay went with its founders, who were sentenced in November 2025 ([US DOJ](https://www.justice.gov/usao-sdny/pr/founders-samourai-wallet-cryptocurrency-mixing-service-sentenced-five-and-four-years)). So any camp with backhaul must be able to act as a gateway, and the design should run at least two in separate locations. The second is that txTenna gave the sender no confirmation path back ([txTenna](https://github.com/remyers/txTenna)). So receipts are mandatory here.

Each gateway does three things. On broadcast, it submits over a fresh Tor circuit per transaction, the way Zodl's Tor mode sends transactions ([Zodl Tor](https://support.zodl.com/article/17-enabling-tor-protection)), after a randomized delay and batched with other traffic. It never broadcasts from a node that also hosts a wallet. After broadcast, it returns a signed receipt. After mining, it returns an inclusion proof: the 1,487-byte header plus a Merkle branch, about 1.7 KB in all ([Zebra header length](https://doc-internal.zebra.zfnd.org/zebra_chain/block/header/constant.BLOCK_HEADER_LENGTH.html)).

The third job is publishing a chain bundle on a shared topic so every camp can stay synced without revealing which transactions interest it. This preserves the ZIP 307 property that compact-block sync is broadcast rather than query ([ZIP 307](https://zips.z.cash/zip-0307)). The bundle contains compact blocks, which include every Ironwood nullifier and commitment ([compact_formats.proto](https://github.com/zcash/lightwallet-protocol/blob/main/walletrpc/compact_formats.proto)), plus headers and treestates. On a quiet testnet the compact blocks are hundreds of kilobytes a day. Full headers come to about 1.9–2.1 MB a day at the observed rate, or 5.1 MB a day at the 25-second target. That is minutes on any HaLow or Wi-Fi link and impossible on duty-cycled LoRa.

ZIP 307 wallets check only `prevHash`, and a malicious server can show fake payments ([Hornby deck](https://defuse.ca/downloads/Fixing%20Privacy%20Problems%20in%20the%20Zcash%20Light%20Wallet%20Protocol.pdf)). Camps should therefore validate Equihash PoW on headers and cross-check bundles from at least two gateways. Well-provisioned camps can go further and run their own zebrad peered only with gateway nodes over the backbone, which gives full local validation of anchors and nullifiers. Testnet chain storage size was not researched.

## Double-spend protection comes from trust or waiting, so acceptance is tiered

No offline recipient can be cryptographically sure an Ironwood note is unspent, for three independent reasons:

- A perfect snapshot of the nullifier set says nothing about spends made after it, on the other side of the partition. This is the CAP argument that Grothoff and Dold apply to offline payments ([Grothoff & Dold](https://git.gnunet.org/taler/marketing/file/papers/2021-offline/offline.tex.html)).
- Zcash headers commit to note commitment roots but not to the nullifier set. A nullifier commitment was considered for ZIP 221 and left out ([ZIP 221](https://zips.z.cash/zip-0221)).
- Whoever holds the spend authorizing key can sign a second spend at any time, and consensus deduplicates nullifiers only at mining.

Zcash engineers have said this bluntly. In the forum thread on offline Zcash payments, nuttycom wrote that "Preventing double-spending is literally the only problem that blockchains solve" ([Zcash forum](https://forum.zcashcommunity.com/t/how-to-pay-offline-with-zcash-in-any-situation/50167)). IBM Research calls offline double-spending "trivial" without connectivity ([ePrint 2024/1746](https://eprint.iacr.org/2024/1746)).

The way out is to notice that "offline" here means *no internet*, not *no network*. When the backbone is up, a payee can reach a local authority in real time. The useful local authority for Zcash is a FROST co-signer. ZIP 312 defines re-randomized FROST(Pallas) spend-authorization signatures for the Orchard protocol. Only the spend authorizing key is threshold-shared, and the signatures are indistinguishable on chain ([ZIP 312](https://zips.z.cash/zip-0312)). The Zcash Foundation's frost-client and frostd are audited ([Least Authority](https://leastauthority.com/blog/zcash-frost-demo/)). ZIP 2005 explicitly defines a key-derivation branch (`use_qsk = true`) for "FROST and hardware-wallet keys" in the Ironwood era ([ZIP 2005](https://zips.z.cash/zip-2005)), so FROST-controlled Ironwood accounts are anticipated by the spec. Whether ZF's tooling already implements that branch is unverified.

The mechanism works like this. While connected, the payer funds an Ironwood **escrow note** whose spend authority is split 2-of-2 between the payer and a co-signer basecamp C, and waits for confirmations. From then on, no spend of that note can exist without C's share. C's append-only registry, keyed by nullifier, is therefore the complete truth about the note even while fully offline. At payment time, C checks the signature hash, records the nullifier, co-signs, and returns an attestation signed with its basecamp key. The payee then needs to trust C, not the payer.

| Acceptance tier | What the payee holds | Stops a payer double-spend? | Trust assumption | Use for |
|---|---|---|---|---|
| Pending | Verified, proven transaction | No | Payer honesty, limits, reputation | Low-value payments between known camps |
| Co-signed (neutral co-signer C) | Transaction plus C's signed attestation | Yes, unless payer and C collude | C honest, available, registry intact | Routine inter-camp payments |
| Bilateral escrow (co-signer is the payee) | Transaction the payee co-signed | Yes | Only the payee's own registry; payer bears payee-liveness risk | Repeated payments between a fixed pair |
| On-chain final | 10 or more confirmations via PoW-validated headers | Yes | Zcash consensus | Every payment, eventually |

The bilateral variant follows from PCZT v2 and is an untested inference. If the payee itself is the co-signer, it trusts nobody but itself. Because PCZT v2 lets participants sign a spend of the escrow's *unmined* change note, the pair can chain several offline payments from one escrow. Every FROST participant holds the full viewing key ([ZF FROST book](https://frost.zfnd.org/zcash/technical-details.html)), so the payee can generate the deferred proofs itself once each parent transaction is mined.

Escrow notes come with costs.

- **Pinning.** Each note must be pinned to exactly one co-signer. If any one of several guardians can co-sign, two guardians can each co-sign a different spend, which recreates the double-spend unless the signing quorums intersect.
- **Visibility.** The co-signer learns the escrow's full viewing key, so it sees amounts and recipients.
- **Liveness.** The notes found no timelocked refund path for shielded notes. If C disappears, the escrow is stuck. Whether a v6 `lock_time` could gate a fully shielded refund is unverified. It may require a transparent input, which an Ironwood-only design excludes.
- **Signing rounds.** FROST signing takes two rounds over the mesh, and the randomizer must travel over a confidential, authenticated channel. The application envelope satisfies this requirement.

Every envelope also carries the payer's basecamp signature over (nullifier, txid, payee). A double-spend that reaches the chain therefore becomes attributable evidence rather than an anonymous loss, because the nullifier match itself is detectable after reconnection. Rerandomized spend signatures alone do not identify the sender.

Several alternatives were weighed and rejected:

- **Secure-element "spend-once" hardware** does not exist for Zcash, and CBDC analyses note that one secure-element break allows unlimited double-spends ([arXiv 2601.18644](https://arxiv.org/html/2601.18644v1)).
- **A basecamp-run ecash mint** works only as a custodial overlay that is not Zcash.
- **ZIP 324 bearer URIs** are Draft and Sapling-based, and they still need a chain lookup to accept. On a multi-hop mesh, interception equals theft ([ZIP 324](https://zips.z.cash/zip-0324)).
- **Lightning-style channels** are not known to exist for the shielded pool.

Testnet TAZ is worthless, so collateral and credit limits can only be simulated.

## One payment traced end to end

The flow below assumes basecamp A pays basecamp B, gateways G1 and G2 have intermittent uplinks, and the IP backbone is up. If the backbone is down, steps 1, 5 and 7 ride the LXMF bridge or a QR or USB courier instead, with the same envelope contents.

| Step | Where | Action | What crosses the mesh |
|---|---|---|---|
| 0 | All camps, while connected | Exchange Logos node keys and envelope keys in person. Fund Ironwood accounts and split them into 10+ confirmed notes. Optionally fund FROST escrow notes. Load the fleet policy file (branch ID `0x77190AD9`, expiry delta, fee, 2-action padding, anchor boundary rule). | Nothing |
| 1 | Payee B | Issue a ZIP 321 request (`zcash:utest…?amount=…`) with an invoice ID ([ZIP 321](https://zips.z.cash/zip-0321)) | One 16 KiB envelope, B→A |
| 2 | Payer A's builder | PCZT v2 Creator and Constructor: v6, Ironwood-only, 2 actions. Anchor at the latest shared boundary height, which ZIP 318 uses to avoid "linking transactions via anchor selection" ([ZIP 318](https://zips.z.cash/zip-0318)). Fleet expiry and fee. | Nothing |
| 3 | A's signer | Keystone signs via QR, or a FROST round runs with co-signer C. C checks its registry, records the nullifier, and returns its share plus a signed attestation. | FROST only: two envelope round trips A↔C |
| 4 | A's builder | Halo 2 proof, binding signature, extract the 9,166-byte transaction and txid | Nothing |
| 5 | A | Seal tx, txid, expiry, invoice ID, attestation and A's intent signature into separate envelopes for B, G1 and G2 | Three 16 KiB envelopes on the shared topic, Store-backed |
| 6 | B | Trial-decrypt the output, recompute `cmx`, verify signatures and proof, check anchor and nullifier against local chain state, verify the attestation | Nothing |
| 7 | B | Signed receipt marked "pending" or "co-signed" | One envelope, B→A |
| 8 | G1 and G2, at their next uplink window | Submit over a fresh Tor circuit after a random delay, batched. Return a signed broadcast receipt. | Envelopes G→A and G→B |
| 9 | Gateway, after mining | Header, Merkle branch and subsequent headers in the chain bundle | Broadcast on the chain topic |
| 10 | A and B | B marks the payment final at 10+ confirmations. A marks the notes spent. If expiry passes unmined, A re-issues spending **the same notes**. | Nothing |

Two failure rules make the flow safe. First, a re-issue must spend the same notes as the stuck transaction. The shared nullifier then guarantees that at most one version is ever mined. Re-paying from *different* notes risks paying twice if the first transaction later lands. Second, sending the same signed transaction through several gateways costs nothing but extra origin exposure, because it is idempotent by txid. After any uplink, each party checks the chain bundle for the payment's nullifiers. If a nullifier appears in a different txid, the payment failed, and the payer's intent signature identifies who tried it. ZIP 315 recommends 10 confirmations for untrusted funds ([ZIP 315](https://zips.z.cash/zip-0315)). Testnet's low hash rate, and its rule allowing minimum-difficulty blocks after a 450-second gap ([ZIP 218](https://zips.z.cash/zip-0218)), argue for more.

## Metadata, not amounts, is the weak flank

Cryptographic confidentiality is strong. A fully shielded Ironwood transaction hides sender, recipient, amount and memo, and the application envelope keeps even the encrypted transaction away from relays. What a v6 transaction still reveals publicly is the nullifiers, note commitments, action count, anchor, expiry height, `valueBalance` and exact size ([ZIP 229](https://zips.z.cash/zip-0229)). Ironwood's formal verification covers soundness and balance, not privacy ([crypto.news](https://crypto.news/zcash-ironwood-upgrade-whats-changed-after-the-orchard-bug/)).

The leaks that matter for this architecture are network- and radio-level. Biryukov and Tikhomirov deanonymized their own Zcash transactions from broadcast timing "with a high level of accuracy", which makes whichever gateway injects a transaction its apparent origin ([Biryukov & Tikhomirov](https://orbilu.uni.lu/bitstream/10993/39724/1/biryukov-tikhomirov-deanonymization-and-linkability)). Long-lived full nodes over Tor face exit-banning and fingerprinting ([Biryukov & Pustogarov](https://arxiv.org/abs/1410.6079)), which is why gateways should submit one-shot over fresh circuits rather than keep a persistent node identity on Tor. On the messaging layer, Waku Relay offers only weak sender anonymity, and only against a single-node attacker. Neighbours receive a node's own messages faster than relayed ones ([Logos Research](https://research.logos.co/rlog/wakuv2-relay-anon)). On a sparse radio mesh where each camp has one or two neighbours, that becomes near-certain origin attribution. At the radio layer, LoRa transmitters can be fingerprinted by deep-learning RF identification, even for previously unseen devices ([Liverpool TIFS 2022](https://livrepository.liverpool.ac.uk/3148161/)). Selective jamming cut a victim's packet reception to 1.3% ([Aras et al.](https://arxiv.org/pdf/1712.02141)).

| Threat | Main adversary | Mitigation in this design | Residual risk |
|---|---|---|---|
| Payer double-spends during the offline window | Dishonest payer | Tiered acceptance; FROST co-signer registry; intent signatures; 10+ confirmations | High at "pending"; becomes trust in the co-signer at "co-signed" |
| Gateway is the first broadcaster | Zcash P2P spies, ISP | Tor with a fresh circuit per transaction; two or more rotating gateways; random delay; batching | Medium. A global passive adversary defeats Tor ([Kappos & Piotrowska](https://arxiv.org/pdf/1902.07337)) |
| Offline fingerprint from stale anchor and long expiry | Chain analyst | Shared boundary-height anchors; one fleet-wide expiry; standard fee; 2-action padding | Medium. The fleet is identifiable as a group. |
| Neighbour timing reveals origin | Malicious mesh node | One shared topic; fixed 16 KiB envelopes; scheduled dummy envelopes; Mix off because its anonymity set would be tiny | Medium–High on small meshes |
| Store and relay nodes log metadata | Store operator | Envelopes with no cleartext recipient; Store only on the fleet's own nodes; capped retention | Medium |
| Sybil or eclipse attack feeding fake chain data | Rogue radio node | Authenticated link layer; static peers; discovery off; PoW-validated headers from two or more gateways | Medium, lower once link-layer authentication is enforced |
| Gateway withholds or time-shifts a transaction | Malicious gateway | Parallel submission; signed broadcast receipts; finite expiry; cancel by re-spending the same notes | Medium |
| Direction finding and RF fingerprinting | Local RF observer | Directional backbone dishes; unattended relays away from people; lowest workable spreading factor; scheduled bursts | High against a determined local adversary |
| Traffic analysis of payment-sized bursts | Local RF observer | Cover traffic (cheap on IP); fixed-size frames | Medium on the backbone, High on LoRa |
| Jamming or duty-cycle exhaustion | Local RF observer | Band diversity; multiple paths; courier fallback; per-peer rate limits | Medium–High |
| Spend-key theft or physical seizure | Malware, captor | Hardware signer or FROST shares; full-disk encryption; no keys on relays | Medium |
| Viewing-key exposure | Server operator, captor | Never share a UFVK; give a UIVK only for watch-only use ([ZIP 316](https://zips.z.cash/zip-0316)); keep minimal history | Medium |
| Delegated proving leaks note data | Prover host | Prove only on the payer's own builder | Low |
| Radio firmware supply chain | Vendor | Re-key on receipt; prefer Reticulum over Meshtastic; end-to-end encryption above the link | Medium |
| Protocol immaturity | All | Testnet only; pinned versions; defence in depth | Medium |

Cover traffic shows why the backbone matters for privacy as well as throughput. One dummy 16 KiB envelope every five minutes per camp costs about **440 bits per second**, and about 66 MB of Store space per camp over a 14-day retention window. That is negligible on a 5 GHz link, yet the same envelope would consume minutes of LoRa airtime. Dummies must be stored like real traffic, because the `ephemeral` flag is visible metadata. Turning RLN off removes two leaks that would otherwise be likely in an intermittently connected mesh. Publishing with a stale membership root reveals a member's tree position. Two messages in one epoch (a split bundle, a retransmit, or one credential shared by a primary and backup device) let any peer reconstruct the member's secret ([17/RLN-RELAY](https://lip.logos.co/messaging/core/draft/17/rln-relay.html)). The price is that spam control rests on link-layer admission and per-peer rate limits. That is acceptable in a closed, operator-controlled fleet, where a malicious insider is the larger risk.

## What "offline" can and cannot guarantee

Offline operation guarantees that a payee receives, within mesh latency, a transaction it can verify cryptographically as paying it a specific amount. When a co-signer is reachable, the payee also receives a credible local guarantee that the payer cannot spend the same note elsewhere. It does not guarantee that ZEC has moved. Settlement happens only when some node reaches the public testnet and the transaction is mined. A fleet that never reaches the public network cannot settle at all. A private chain mined inside the mesh would be a fork, not the current Zcash testnet.

The "pending" tier is an IOU backed by the payer's honesty. The "co-signed" tier converts double-spend risk into trust in one co-signer, plus that co-signer's availability, because the notes found no shielded refund path if it vanishes. Offline claims are also fragile over time. They die at their expiry height, or if a network upgrade changes the branch ID first. Chained offline payments (A pays B, B pays C before A's transaction is mined) can be signed but not proved until each parent is mined, so the risk compounds with every hop.

Verification has limits too. A recipient without validated chain state cannot rule out a proof against a fabricated tree. A recipient whose chain data comes from one gateway is trusting that gateway. Metadata protection has hard floors: no cryptography hides that a radio transmitted, from roughly where, and at what time. The realistic anonymity set for timing and anchor fingerprints is "the fleet's users", not "all Zcash users".

Finally, much of the stack is not finished:

- ZIPs 229, 258, 318 and 326, and PCZT v2, still carry Draft status in the 2026-09-30 snapshot, and ZIP 2005 is Proposed.
- Zebra 7 is a release candidate.
- Logos Delivery is pre-1.0, its Store Sync, Mix, Noise and reliable-channel specs are "raw", and no third-party audit of v0.39 was found.

Tachyon's out-of-band payments and oblivious sync would map neatly onto mesh delivery, but they remain an unshipped proposal ([Sean Bowe, Tachyon](https://seanbowe.com/blog/tachyon-scaling-zcash-oblivious-synchronization/)).

## A five-phase testnet proof of concept retires the unknowns

The plan front-loads the cheapest checks that could kill the design. Can a wallet produce Ironwood v6 transactions on post-NU7 testnet at all? Does a stale-anchor, long-expiry transaction built days offline actually get mined? Only after those pass does it spend effort on radios.

Three unknowns gate the schedule and should be tested first: wallet support for testnet after NU7, Raspberry Pi proving cost, and FROST tooling for Ironwood. No source answers any of them, and each one changes the hardware or protocol choices that follow.

## Conclusion

The design lever that matters most is a reframing. A basecamp mesh is not offline in the sense that makes payments impossible. It lacks the internet, not a network, and it can host a reachable local authority. That turns "prove a note is unspent while partitioned", which is unsolvable, into "ask the co-signer that holds half the spend authority", an ordinary online check over a local link. Ironwood's v6 changes then make delayed settlement unusually clean. Anchors are authorizing data with no age limit, transactions can be signed before they are anchored, and proving needs no parameter files. The binding constraints on an offline Zcash payment are therefore expiry heights, branch-ID epochs and pre-split note inventory, not chain freshness.

The bandwidth picture also inverts the usual intuition. Payment payloads are small (9 KB fits comfortably in one Logos message), while chain state and metadata protection are the expensive parts. Cover traffic and header sync are cheap on a 5 GHz or HaLow backbone and impractical on duty-cycled LoRa. That, more than throughput, is why LoRa should stay a fallback. What remains to build is narrow and novel: the envelope, receipt and gateway service, the chain-bundle format with PoW validation, and the co-signer registry. No existing implementation of any of these was found. Everything else is configuration of software that already exists, which makes a testnet proof of concept a realistic near-term project rather than a research program.
